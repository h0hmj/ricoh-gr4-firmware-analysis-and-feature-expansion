# GR IV 1.11 闪光灯与热靴控制检查

后续已进一步还原命令字段、自动输出公式及 kind 0x11 专用校正，详见[新热靴协议深入报告](2026-10-12-gr4-hotshoe-protocol.md)。本篇保留第一轮的证据范围与验证状态。

## 问题与结论

2026-10-12 对本地 GR IV 固件重点检查闪光灯设置、曝光参数转换、拍摄等待和热靴通信。**已确认闪光灯相关代码确实有执行路径，并非只有菜单字符串；尚未确认具体缺陷，也没有证明可以通过一个开关解锁 P-TTL、无线闪光或 HSS。**

本轮最明确的发现：

- `AUTO / 1/1 / 1/4` 分别是输出设置 ID `0 / 1 / 2`。后两项转换成手动控制与 `0 / −2 EV` 的曝光计算参数。
- 慢速同步 `2 / 3` 在曝光模式不允许自动快门时回退为强制闪光 `0 / 1`，保留原来的红眼选择。
- GR IV 的默认 ProjectType 为 `2`，选择新的 `HotshoeControl` 路径；旧闪光通信的超时处理不能直接当作 GR IV 的实际故障表现。
- 新路径包含附件检测、识别握手、数据读取和命令输出。实际附件型号与内部编号、出光量和引脚时序仍待实测。

证据类型为**静态分析**。没有连接相机、触发闪光或修改固件。下面的地址都是该样本的 RTOS 运行时映射地址，并非此次从相机读取的地址。

## 设置到曝光参数的路径

| 运行时地址 | 含义与证据 |
| --- | --- |
| `0x53399C1C` | `GetFlashControlValueAscii`：ID 0 输出 AUTO，1 输出 1/1，2 输出 1/4；其他 ID 进入断言路径 |
| `0x53DBB070` | 菜单输出顺序的三个字节为 0、1、2；ADJ 路径 `0x531BE528` 按索引读取并调用上述格式化函数 |
| `0x5329DE48` | `CreateCommonPropertyFlashCorrectValue`，读取原生 UserData 对象 `+0xC00` 的输出设置 |
| `0x5329DEE0` | `CreateCommonPropertyFlashControl`，把输出设置转换成自动/手动控制字节 |
| `0x5329E108` | 调用前两项，并将浮点参数发布到公共属性 `+0xA0`，控制字节发布到 `+0xA4` |

转换结果如下，字段偏移均相对各自对象，不是可直接写入相机的绝对 RAM 地址：

| 拍照输出 ID | 显示 | 公共控制值 | 公共闪光校正参数 |
| --- | --- | --- | --- |
| 0 | AUTO | 0 | UserData `+0xBFC` 的既有浮点值 |
| 1 | 1/1 | 1 | `0.0` |
| 2 | 1/4 | 1 | `−2.0` |

UserData `+0xB1E` 的视频标志非零时，两项强制变为 `0 / 0.0`。无效输出 ID 在拍照路径触发诊断断言，后续代码有零值回退；是否终止、忽略或继续由断言服务决定，本轮未测试其运行行为。

**解释：**四分之一能量相对全功率是低两档，与 `−2.0` 一致。这证明设置在曝光参数层面的含义，不证明 GF-2 的电路只存在两档功率，更不能把此浮点值直接解释成发光时间或通信字节。AUTO 仍保留内部校正值；这也不证明用户能从当前菜单调节连续闪光补偿。

## 慢速同步与红眼

字符串解析器 `0x533F2FE8` 明确把 `Force / ForceRedEye / SlowSync / SlowSyncRedEye` 转为 `0 / 1 / 2 / 3`。

`FlashModel::IsEnableSet` 位于 `0x533E005C`：前两种模式直接允许；后两种调用曝光模式解码器 `0x53256D78`，依据其 Tv 自动标志决定是否允许。`ReplaceFlashMode` 位于 `0x533E0114`：不允许时 `2 → 0`、`3 → 1`。`0x532A86C8` 的属性整理路径确实调用该回退函数。

这与官方说明的 Tv/M 不能选慢速同步相符。它不是取消红眼的机制，也不是新增后帘同步的证据。

## 曝光计算与拍摄等待

在 RTOS 中定位到有代码引用的 `AeFlashAlgorithm`、`AeFlashSetupPrepare`、`AeFlashSetup`、`AeProgramDiagramFlash`、`AeFlashComData`，并通过源码路径诊断字符串和 C++ 类型信息关联它们。主要初始化入口分别为 `0x53678188`、`0x53679438`、`0x53679FCC`、`0x5367D1C8`、`0x5367FC60` 附近；最后一项仅为调查范围定位，未精确确定函数起点。

`AeProgramDiagramFlash` 初始化保存 `m_lensState`，并在 `0x5367E4A8` 调用镜头状态接口 `0x53942980`，结果参与浮点参数计算。**这是镜头状态参与计算的证据，不足以给该返回值指定“米”或确认完整的 GN/距离/ISO 公式。**官方关于按被摄距离调整 GN 和 ISO 的描述需作为独立资料对照，不能代替数据字段还原。

拍摄状态名称映射明确列出：

- `0x32D`：`RELEASE_STEP_FLASH_CHARGE_CHECK`；名称映射在 `0x53663EB8`。
- `0x32E`：`RELEASE_STEP_FLASH_CHARGE_WAIT`；名称映射在 `0x53663E94`。
- `RELEASE_STEP_AE_FLASH_COM_BEFORE_SHUTTER`、`RELEASE_WAIT_FACTOR_FLASH_COM_COMPLETE`，及红眼发光/等待状态。

`0x53662D30`、`0x53662D5C` 将两个充电状态注册到拍摄步骤构造器；等待项的参数包括 `0x200000` 和 `0x1E`。**尚未还原参数单位、具体处理函数和 GR IV 当前拍摄模式的完整可达性**，所以不能据此称为“30 秒充电超时”。红眼预闪与用于测光的 P-TTL 预闪也必须区分。

## GR IV 选择哪种热靴通信

ProjectProperty 默认表 `0x53FE50D0` 包含 ProjectType `2`、配置编号 `0x27C` 和标准 GR IV 产品 ID `0x132E0`。`0x538E7D1C` 选择默认表；`0x538E7D94` 的型号整理路径分别处理 HDF、Monochrome 等产品表；`0x538E7FD0` 从当前表读取 ProjectType。

`FlashInterface` 初始化 `0x53771CC4` 做明确分支：

- ProjectType 在 `2…6`：对象 `+0x54 = 1`，使用热靴工厂返回的 `+8` 对象，保存到接口对象 `+0x48`。
- 其他 ProjectType：`+0x54 = 0`，使用工厂 `+4` 对象，保存到接口对象 `+0x44`。

标准 GR IV 的静态配置符合第一条。未读回当前机身的运行时表，不能把这个结果推广到所有改过工厂配置的机身。

新路径有以下实质内容：

| 运行时地址 | 静态行为 |
| --- | --- |
| `0x53A729C0` | HotshoeControl 初始化；绑定 AD 数据、计时器、FlashDataManager 及 HotSclk/HotScs/HotSdai/HotSdao、SIO 等接口 |
| `0x53A731C4` | 读取检测值，乘 180 后右移 10 位，以 134/106/75/45/15 阈值分为 1…6；输入有效标志为零时返回 0 |
| `0x53A73250` | `CheckAccessoryAttachment`：结合检测分档选择通信模式，模式字段在对象 `+0x30`；0/6 分档进入未识别路径 |
| `0x53A7308C` | 通信传输：使用 SIO、片选和计时接口，按命令传输数据字节 |
| `0x53A73334` | 模式 1 发送识别命令；回复首字节须为 `0xA5`，否则清空相关识别状态 |
| `0x53A73404` | 第二次识别返回 kind/subkind；kind 为 `0x11` 或 `0x12` 时设置协议状态 `0x10` |
| `0x53A73448` | 输入读取要求通信模式为 1、协议状态为 `0x10`；否则返回 0 |
| `0x53A73638` | 输出分派也检查上述条件；根据相机状态发送数据，部分状态拒绝或直接返回成功 |

命令表位于 `0x54354054`，按“命令字节 / 数据字节数”排列：`C0/1, C1/2, C2/2, C3/2, C4/2, C5/1, A0/1, A1/1, A2/1, A3/1, A4/1, A5/1, A6/2`，随后是零终止项。此表及调用点已核对；**尚不能给每个命令命名为功率、充电、GN 或触发命令，也不能确认 0x11/0x12 分别是哪款附件。**

有专门针对 kind `0x11` 的参数调整代码，例如 `0x53771ED8` 和 `0x537720F8`，不是简单地原样转发菜单 ID。由于还没有物理功率/距离和通信字节对照，本轮不声称已还原 GF-2 调光曲线。

## 超时、异常与旧代码的限制

`FlashInterface` 输入 `0x53771F88`、输出 `0x53772204` 都先检查接口标志 `+0x54`。标志非零时分别走 `0x53A73448`、`0x53A73638` 的新路径；标志为零时走旧通信轮询。

旧路径存在计时返回值大于 `10` 的超时判断，打印 `ExtFlashInput TIMEOUT` / `ExtFlashOutput TIMEOUT CameraState`，调用 `0x53A72620 → 0x53A6DAC0` 清理，并返回 0。清理函数包含协议状态置 `0xFF` 和多个服务调用。计时单位及所有清理效果未完全还原；上述日志不能据此描述为 GF-2 已实测的超时行为。

固件还包含 `m_ResultWdPreFlash`、`WirelessFlashChannel`、`InternalFlash` 等名称，以及多 ProjectType 和硬件变体的分支。它们**不证明 GR IV 装有内闪或支持无线/P-TTL**。本次也没有证据证明 P-TTL 完全可以靠固件恢复，或证明它在硬件上绝对不可能。

## 结果与后续验证

本轮已完成包头/校验复查、设置转换与模式回退追踪、新旧热靴接口分流和握手/命令表定位。**没有确认可修复的闪光灯 bug，没有新增兼容性结论，也没有实机或硬件时序验证。**

进一步定位故障时，最有价值的是固定拍摄模式/ISO/光圈/距离，以 AUTO、1/1、1/4 分别取样，将实际亮度、附件识别状态、曝光公共参数和通信结果对应起来。另一条独立方向是追踪充电等待、通信返回失败后的上层处理以及电子快门与 X 同步门控。修改识别阈值、假冒附件型号或直接放宽等待/输出分支都不能替代这些证据。

本轮不写设备，没有设备恢复操作。原始包与解码载荷未改动。局部 ARM 模拟代码已准备，但其验证状态仍是未执行。
